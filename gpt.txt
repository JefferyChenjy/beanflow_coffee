# 1. First: turn the Coffee Shop into a real business case

Instead of making this just an AWS technical demo, I would frame it as a real business problem.

## Business: Smart Coffee Shop Operations Platform

Imagine a coffee chain called **BeanFlow Coffee**.

Customers order through:

* Mobile App
* Self-service kiosk
* Website
* GrabFood / delivery platform

Every order generates an event:

```json
{
  "event_type": "ORDER_CREATED",
  "order_id": "ORD-10025",
  "store": "SG-ORCHARD",
  "customer": "Jeff",
  "items": [
    {
      "name": "Iced Latte",
      "quantity": 1
    },
    {
      "name": "Blueberry Muffin",
      "quantity": 1
    }
  ],
  "total": 12.50,
  "timestamp": "2026-08-10T18:00:00+08:00"
}
```

The business wants different teams to react to this event.

### Store team

Needs to know:

> "New order received!"

They use **Discord** as the store operations channel.

### HQ / Operations team

Needs:

> "Order activity / operational event"

They use **Slack**.

### The problem

A naive architecture is:

```text
Order App
    |
    +----> Discord
    |
    +----> Slack
```

This creates tight coupling.

If Discord is temporarily unavailable:

```text
Order App ---> Discord ❌
```

Now your order application is dependent on Discord.

That's exactly the **synchronous trap** your Keynote describes.

---

# 2. The improved business architecture

We introduce SNS and SQS.

```text
                         ┌── SQS: Discord Queue ──> Lambda ──> Discord
                         │
Order Application ──> SNS Topic
                         │
                         └── SQS: Slack Queue ───> Lambda ──> Slack
```

The important business idea is:

> **The order system doesn't care whether Discord or Slack is available.**

It publishes an event and moves on.

SNS handles the **fan-out**.

SQS handles **buffering**.

Lambda handles **processing/integration**.

That's a very clean explanation for your presentation.

# 7. Step 2 — Create SNS

Create:


```hcl
resource "aws_sns_topic" "order_events" {
  name = "beanflow-order-events"

  tags = {
    Project = "BeanFlow"
    Purpose = "Coffee Order Events"
  }
}
```

Conceptually:

```text
Coffee Order
     |
     v
SNS
```

SNS is the **event broadcaster**.

AWS describes SNS as supporting fan-out to multiple subscribers, while SQS provides persistent queues for asynchronous processing. ([Terraform Registry][1])

# 8. Step 3 — Create the two SQS queues

Create:

```text
terraform/sqs.tf
```

```hcl
resource "aws_sqs_queue" "discord" {
  name = "beanflow-discord-queue"

  visibility_timeout_seconds = 60

  tags = {
    Project = "BeanFlow"
    Consumer = "Discord"
  }
}

resource "aws_sqs_queue" "slack" {
  name = "beanflow-slack-queue"

  visibility_timeout_seconds = 60

  tags = {
    Project = "BeanFlow"
    Consumer = "Slack"
  }
}
```

Now:

```text
                    SNS
                     |
             +-------+-------+
             |               |
             v               v
        Discord SQS      Slack SQS
```

This is the key architectural improvement.

If Discord stops responding:

```text
SNS
 |
 v
Discord SQS
 |
 |  messages wait
 |
 X Discord temporarily unavailable
```

The messages aren't simply lost.

# 9. Step 4 — SNS → SQS subscriptions

Now we tell SNS:

> Whenever a coffee order event arrives, send a copy to both queues.

```hcl
resource "aws_sns_topic_subscription" "discord" {
  topic_arn = aws_sns_topic.order_events.arn
  protocol  = "sqs"
  endpoint  = aws_sqs_queue.discord.arn

  raw_message_delivery = true
}

resource "aws_sns_topic_subscription" "slack" {
  topic_arn = aws_sns_topic.order_events.arn
  protocol  = "sqs"
  endpoint  = aws_sqs_queue.slack.arn

  raw_message_delivery = true
}
```

Terraform's AWS provider specifically supports SNS → SQS subscriptions; this is one of the standard SNS/SQS fan-out patterns. ([Terraform Registry][2])

But we're **not finished**.

AWS needs permission for SNS to put messages into these queues.

# 10. Step 5 — SQS policies

This is actually a good part to explain during the demo because it shows you understand AWS IAM rather than simply copying Terraform.

Add:

```hcl
data "aws_iam_policy_document" "discord_queue_policy" {
  statement {
    effect = "Allow"

    principals {
      type        = "Service"
      identifiers = ["sns.amazonaws.com"]
    }

    actions = [
      "sqs:SendMessage"
    ]

    resources = [
      aws_sqs_queue.discord.arn
    ]

    condition {
      test     = "ArnEquals"
      variable = "aws:SourceArn"
      values = [
        aws_sns_topic.order_events.arn
      ]
    }
  }
}

resource "aws_sqs_queue_policy" "discord" {
  queue_url = aws_sqs_queue.discord.url
  policy    = data.aws_iam_policy_document.discord_queue_policy.json
}
```

And similarly for Slack:

```hcl
data "aws_iam_policy_document" "slack_queue_policy" {
  statement {
    effect = "Allow"

    principals {
      type        = "Service"
      identifiers = ["sns.amazonaws.com"]
    }

    actions = [
      "sqs:SendMessage"
    ]

    resources = [
      aws_sqs_queue.slack.arn
    ]

    condition {
      test     = "ArnEquals"
      variable = "aws:SourceArn"
      values = [
        aws_sns_topic.order_events.arn
      ]
    }
  }
}

resource "aws_sqs_queue_policy" "slack" {
  queue_url = aws_sqs_queue.slack.url
  policy    = data.aws_iam_policy_document.slack_queue_policy.json
}
```

The explicit `2012-10-17` policy version is important with SQS policies; the Terraform provider documentation calls this out as well. ([Terraform Registry][3])

# 12. Lambda IAM role

Create:

```text
terraform/iam.tf
```

```hcl
data "aws_iam_policy_document" "lambda_assume_role" {
  statement {
    effect = "Allow"

    principals {
      type        = "Service"
      identifiers = ["lambda.amazonaws.com"]
    }

    actions = [
      "sts:AssumeRole"
    ]
  }
}

resource "aws_iam_role" "lambda" {
  name = "beanflow-notification-lambda-role"

  assume_role_policy = data.aws_iam_policy_document.lambda_assume_role.json
}
```

Then CloudWatch logging:

```hcl
resource "aws_iam_role_policy_attachment" "lambda_logs" {
  role       = aws_iam_role.lambda.name
  policy_arn = "arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole"
}
```

# 13. Package the Lambda with Terraform

Create:

```hcl
data "archive_file" "lambda" {
  type        = "zip"
  source_file = "${path.module}/../lambda/index.mjs"
  output_path = "${path.module}/lambda.zip"
}
```

Terraform's `archive_file` data source/resource is designed for exactly this type of Lambda ZIP packaging. ([Terraform Registry][5])

Then:

```hcl
resource "aws_lambda_function" "notification_processor" {
  function_name = "beanflow-notification-processor"

  filename         = data.archive_file.lambda.output_path
  source_code_hash = data.archive_file.lambda.output_base64sha256

  role = aws_iam_role.lambda.arn

  handler = "index.handler"
  runtime = "nodejs24.x"

  timeout     = 30
  memory_size = 128

  tags = {
    Project = "BeanFlow"
  }
}
```

# 14. Connect SQS to Lambda

This is the other important Terraform resource:

```hcl
resource "aws_lambda_event_source_mapping" "discord" {
  event_source_arn = aws_sqs_queue.discord.arn
  function_name    = aws_lambda_function.notification_processor.arn

  batch_size = 1

  enabled = true
}

resource "aws_lambda_event_source_mapping" "slack" {
  event_source_arn = aws_sqs_queue.slack.arn
  function_name    = aws_lambda_function.notification_processor.arn

  batch_size = 1

  enabled = true
}
```

AWS Lambda polls the SQS queues and invokes the function when messages arrive; Terraform manages that connection through `aws_lambda_event_source_mapping`. ([Terraform Registry][6])

So now your infrastructure is:

```text
                 ┌── Discord SQS ──┐
                 │                 │
Coffee Order → SNS                Lambda
                 │                 │
                 └── Slack SQS ────┘
                                   │
                              Processing
```

# 24. But I want to add ONE important improvement

Your Keynote architecture shows:

```text
SQS
 ↓
Lambda
 ↓
Discord / Slack
```

I'd keep that architecture for the presentation because **you asked to match Keynote #9**.

But internally, I'd make the implementation slightly more robust:

```text
                 SNS
                  |
        ┌─────────┴──────────┐
        ↓                    ↓
 Discord SQS             Slack SQS
        ↓                    ↓
 Discord Lambda           Slack Lambda
        ↓                    ↓
     Discord                Slack
```

Why?

Because otherwise one Lambda failure can affect both integrations.

For example:

```text
Discord webhook broken
       ↓
Lambda fails
       ↓
Slack notification also affected
```

With separate consumers:

```text
Discord failure
      ↓
Discord queue keeps retrying

Slack
  ↓
continues working
```

That is a more production-ready microservices architecture.

**But don't start there.**

For your live demo, I recommend:

### Version 1 — exactly like Keynote

```text
SNS
 ↓
SQS × 2
 ↓
Lambda
 ↓
Discord + Slack
```

Then at the end say:

> "For production, I would split the Lambda consumers so that failure in one notification channel doesn't affect the other."

That demonstrates architectural thinking, rather than simply following a diagram.
